# v0.1.0-rc.1 installation walkthrough

Status: ready for independent trials. This protocol tests the published release rather than a checkout-built binary. Complete it in a fresh directory and record any assistance or deviation in the result template at the end.

Expected time to the first passing test after prerequisites are available: about ten minutes. This is an onboarding target, not a performance claim.

## Before starting

You need one of these advertised hosts:

| Host | Shell used below | Release archive |
| --- | --- | --- |
| Linux amd64 | POSIX `sh` | `playtestr_0.1.0-rc.1_linux_amd64.tar.gz` |
| macOS arm64 | POSIX `sh` | `playtestr_0.1.0-rc.1_darwin_arm64.tar.gz` |
| Windows amd64 | Windows PowerShell 5.1 or newer | `playtestr_0.1.0-rc.1_windows_amd64.zip` |

The binary-only route does not require Go, Git, Gum, Python, Node, or the Playtestr source repository. The example target uses `/bin/sh` on Linux/macOS or Windows PowerShell on Windows. These are target prerequisites rather than Playtestr dependencies.

Playtestr executes the command declared in the spec with your user permissions. Use only targets you trust. The runner is not a sandbox, and a target can print sensitive data into failure evidence.

## 1. Download and verify

Open the [v0.1.0-rc.1 release](https://github.com/Wyrcan-io/playtestr/releases/tag/v0.1.0-rc.1). Download the archive for your exact host and the adjacent file with the same name plus `.sha256`. Do not use an archive for a different OS or CPU architecture.

On Linux:

```sh
sha256sum --check playtestr_0.1.0-rc.1_linux_amd64.tar.gz.sha256
tar -xzf playtestr_0.1.0-rc.1_linux_amd64.tar.gz
./playtestr_0.1.0-rc.1_linux_amd64/playtestr --version
```

On macOS:

```sh
expected=$(awk '{print $1}' playtestr_0.1.0-rc.1_darwin_arm64.tar.gz.sha256)
actual=$(shasum -a 256 playtestr_0.1.0-rc.1_darwin_arm64.tar.gz | awk '{print $1}')
test "$actual" = "$expected"
tar -xzf playtestr_0.1.0-rc.1_darwin_arm64.tar.gz
./playtestr_0.1.0-rc.1_darwin_arm64/playtestr --version
```

On Windows:

```powershell
$archive = 'playtestr_0.1.0-rc.1_windows_amd64.zip'
$expected = (Get-Content "$archive.sha256").Split()[0]
$actual = (Get-FileHash $archive -Algorithm SHA256).Hash.ToLowerInvariant()
if ($actual -ne $expected) { throw 'Playtestr archive checksum mismatch' }
Expand-Archive $archive -DestinationPath .
& '.\playtestr_0.1.0-rc.1_windows_amd64\playtestr.exe' --version
```

Stop before extraction if the checksum differs. Every version command above must print `playtestr v0.1.0-rc.1`. Record the exact archive and hash from your machine.

## 2. Optionally use a temporary PATH

Using the binary by its explicit path is sufficient. To test ordinary command lookup without making a permanent machine change, add only the extracted directory for the current shell.

Linux:

```sh
PATH="$(pwd)/playtestr_0.1.0-rc.1_linux_amd64:$PATH"
export PATH
playtestr --version
```

macOS:

```sh
PATH="$(pwd)/playtestr_0.1.0-rc.1_darwin_arm64:$PATH"
export PATH
playtestr --version
```

Windows:

```powershell
$playtestrDirectory = (Resolve-Path '.\playtestr_0.1.0-rc.1_windows_amd64').Path
$env:Path = "$playtestrDirectory;$env:Path"
playtestr.exe --version
```

Closing this shell discards the temporary PATH change.

## 3. Create a harmless target and spec

Create a separate directory named `playtestr first test`. Work inside it so paths containing spaces are exercised.

On Linux or macOS, create `hello.sh`:

```sh
#!/bin/sh
printf 'Name: '
IFS= read -r name
printf 'Hello, %s!\n' "$name"
```

Run `chmod +x hello.sh`. Create `hello.json`:

```json
{
  "version": 1,
  "name": "shell greeting",
  "command": ["./hello.sh"],
  "steps": [
    {"expect": "Name:"},
    {"text": "terminal tester"},
    {"key": "Enter"},
    {"expect": "Hello, terminal tester!"},
    {"exit": 0}
  ]
}
```

On Windows, create `hello.ps1`:

```powershell
$name = Read-Host 'Name'
Write-Host "Hello, $name!"
```

Create `hello.json`:

```json
{
  "version": 1,
  "name": "PowerShell greeting",
  "command": ["powershell.exe", "-NoProfile", "-ExecutionPolicy", "Bypass", "-File", "./hello.ps1"],
  "steps": [
    {"expect": "Name:"},
    {"text": "terminal tester"},
    {"key": "Enter"},
    {"expect": "Hello, terminal tester!"},
    {"exit": 0}
  ]
}
```

Run from the directory containing both files:

```text
playtestr test --report results.json hello.json
```

Expected outcome: six passing steps on Linux/macOS or five passing steps on Windows, `PASS` for the named test, process exit status 0, and `results.json` with `summary.passed` equal to 1.

## 4. Recognize a failure and its evidence

Change the final expected text in `hello.json` from `Hello, terminal tester!` to `Hello, wrong!`. Run the same command again and record the shell exit status.

PowerShell displays it with:

```powershell
Write-Host "Exit code: $LASTEXITCODE"
```

POSIX shells display it with:

```sh
printf 'Exit code: %s\n' "$?"
```

Expected outcome: exit code 1, a `FAIL` line that names the failing step, `hello.json.actual.txt` beside the spec, and a failed entry in `results.json`. The target exits before the unmatched assertion, so this particular short target can report `unexpected_exit`; a long-running target would normally reach `assertion_timeout`.

Open the final-screen text and inspect the report. Do not share them before checking for application data you consider sensitive.

## 5. Restore and rerun

Restore `Hello, terminal tester!` and run the command again. Expected outcome: exit code 0 and a new `results.json` whose summary records one pass and no evidence path.

In v0.1.0-rc.1, an adjacent `.actual.txt` file from the earlier failure is retained after a later pass. It is historical evidence and is not referenced by the new passing report. Remove it after reviewing it:

```text
hello.json.actual.txt
```

Record whether this distinction was clear without help. Do not infer the current result from an old adjacent artifact; use the latest command status and report.

## 6. Check one missing prerequisite

Temporarily change the first command value in the spec to a name that is not installed, such as `playtestr-target-does-not-exist`. Rerun it.

Expected outcome: exit code 1 and `launch_failure` in `results.json`. A missing target never counts as a passing terminal test. Restore the original command afterward.

If a report destination is a directory or otherwise cannot be written, the target may finish but Playtestr exits 1 and prints `FAIL write report:`. It does not claim that the requested report was saved.

## 7. Cancellation check

For an application that remains open, start a test and press Ctrl+C once while Playtestr is running. Expected outcome: Playtestr reports process-tree cleanup and exits 130. Record the target used and whether any child remains. Do not use a production service for this check.

The greeting target can exit too quickly for a useful manual cancellation, so use a trusted long-running local TUI if one is already available. The published bytes have separate automated cancellation and process cleanup coverage; omitting this optional participant exercise must be recorded rather than replaced with an invented result.

## 8. Remove walkthrough files

Close the shell if you changed PATH. Remove only the extracted `playtestr_0.1.0-rc.1_<os>_<arch>` directory, the downloaded archive and checksum, and the `playtestr first test` directory you created. Confirm another file placed beside those directories remains untouched.

Playtestr installs no service or global configuration. If you copied its binary elsewhere manually, remove that copy separately.
