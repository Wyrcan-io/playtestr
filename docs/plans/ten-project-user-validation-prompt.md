# Execute ten real-project user journeys and general Playtestr improvements

Prepared 7 October 2026. This is a reusable execution prompt. Creating or reading it does not start validation. Its implementation and cleanup authorization applies when the user explicitly invokes it.

## Objective and scope

Select ten distinct independently maintained open-source CLI/TUI repositories from GitHub. Use each application as an ordinary new Playtestr user would: install/build it, choose worthwhile workflows, record them, review/export tests, replay from fresh synthetic state, diagnose failures, and maintain intentional expectations. Find friction and defects, implement general Playtestr improvements, verify them, finish that project's evidence, and only then move to the next project.

Complete all ten project journeys. Do not stop after candidate discovery, a demo, a test plan, the first successful application or a documentation-only report. This is the early reliability portion of P5, pulled forward before P3/P4. It does not implement paid integration, billing, cloud hosting or launch, and does not qualify the unfinished complete product for the later 100-project campaign.

No LLM dependencies, AI inference, application-name switches, hidden per-project behavior, automatic baseline acceptance or weakened assertions. Product code may not special-case repository names, executable names, framework names, fixture paths or target output to manufacture success. Ordinary application-specific specs, fixtures, setup recipes and diagnostic evidence are expected; they are not core implementation exceptions.

## Select ten projects autonomously

Prefer maintained, practical applications with local workflows and synthetic inputs; do not choose ten near-identical Go demos.

## Per-project execution order

Work sequentially, with one active target checkout. For each project:

1. Acquire exact source in a uniquely named task-owned temporary directory. Record acquisition hash, upstream URL/license and documented build instructions. Build/install the actual application without editing it for the passing user journey. Record target binary hash and install/build output. Use an unmodified clean build as the baseline.
2. Follow the current public Playtestr docs as a new user. Use a fresh directory and synthetic HOME/config/temp/workspace; avoid leaked developer settings. Actually install or build the identified Playtestr candidate through its documented route. Start with public CLI commands. Do not use private runner APIs or undocumented shortcuts to claim a successful user journey. An independent bounded oracle may supplement the journey to inspect saved state.
3. Explore the real application briefly. Choose three valuable bounded scenarios: a primary happy path, a cancellation/invalid-input/boundary path, and a second meaningful outcome appropriate to it. Prefer selecting/opening an item, filtering/searching, editing/saving synthetic content, changing state, navigating panels, intentional failure and clean exit. Three cosmetic variations of one trivial command do not suffice. Explain the user risk each scenario catches.
4. Write an explicit scope table: what to test, positive evidence, fixture/state needed, why it matters, what not to test and why. Exclude irrelevant features, credential/network flows, randomized/time-dependent content without supported deterministic setup, unsupported mouse/style/grapheme behavior and claims that cannot be observed. Do not label excluded features covered.
5. Record using the public recorder. Capture real input/key/resize behavior, meaningful fresh checkpoints, exact declared exit where applicable and carefully chosen reviewed snapshots. Identify confusing setup, documentation gaps, control collisions, stale anchors, ambiguous screens, dirty fixture state and unsupported input. A wait/sleep, quiet output or successful process launch alone is not proof. Do not silently strip arbitrary dynamic text to make snapshots pass.
6. Inspect candidate steps and every baseline, replay from fresh state, and export ordinary strict v1/v2 specs. Verify no unintended files, secrets or environment values were retained. Demonstrate meaningful edit/rerecord maintenance and ordinary manual JSON editing/replay. Generate and inspect the project's free workflow using explicit build/prerequisite/suite choices; run its same test commands locally. Record actual hosted results only when authorized and executed. A generated workflow is setup evidence, not a real PR result. Refuse silent overwrite or bulk baseline acceptance.
7. Run each selected scenario at least ten times from fresh fixture/home/temp/process state, varying supported inputs/data sizes and readiness conditions without changing intended behavior. Use application-supported delay controls where available; otherwise record external load/ordering variations honestly. Do not call repeated retries delay variation. Preserve the first failure and denominator; retries cannot hide intermittent failures.
8. Prove a real negative outcome with unchanged spec/baselines: an application-supported alternate configuration or a minimal documented temporary source behavior mutation in a separate disposable build. Preserve an exact unified patch/build recipe, source and binary identities. It must alter tested target behavior; breaking an assertion or replacing the target with a fake wrapper is not target-regression evidence. Restore original application bytes/configuration and prove recovery with the same contract hashes. Preserve the unmodified user journey separately from the intentional defect build. Inspect independent persisted state for saved-file/Git workflows before workspace teardown; a target's own success message is insufficient.
9. Demonstrate intentional expectation maintenance on one named checkpoint where meaningful: explicit intended behavior change, visibly reviewed selected baseline update and rerun. Keep this separate from defect recovery; never fix an accidental defect by accepting its snapshot. Record if an application cannot provide a safe useful intentional-change example rather than manufacture one.
10. Classify every finding as Playtestr defect, onboarding/documentation friction, application behavior, unsupported product capability or environment prerequisite. Record severity, reproduction, expected/observed behavior, evidence and proposed general solution. Unsupported behavior must be actionable, never silently dropped. Bound hang/flood/input/cancellation checks relevant to the application; preserve exact failure categories and cleanup status.
11. Implement every actionable in-scope Playtestr fix before advancing. Build the smallest general change, with a reduced deterministic helper regression where possible; verify the failing external journey afterward. Use real PTYs for input/VT/lifecycle changes and run race checks for concurrency. Avoid embedding external application source in Playtestr tests. Document general public behavior and strict contract implications in the same change. Investigate failures rather than immediately increasing deadlines. Record necessary test-only instrumentation budgets separately from product behavior.
12. Recheck earlier retained projects affected by a general change. Reacquire exact source from retained recipes in a new temporary directory, run the relevant scenarios and delete it again. Do not keep old checkouts for convenience. Never claim old binaries qualified a new behavior. Update source/evidence associations and preserve original reports.
13. Close the project report with supported outcomes, exclusions, all failed attempts, repairs, remaining limitations, practical authoring steps and evidence counts. Verify cleanup, capture retained evidence, then remove the task-owned target application directories/builds/caches. Record removed paths and outcomes. Only then proceed to the next project.

## Generalization and scope discipline

Set resource bounds before each target: default build/setup timeout 20 minutes, per-step replay timeout no more than 30 seconds, whole-scenario budget no more than two minutes, and retained raw evidence budget 64 MiB per project. Retain compact failure reports and useful screens first; record any truncation. A justified target-specific adjustment must be explicit in its recipe/evidence before running, never an unbounded retry or a silent product-deadline increase. Bound any target-local service startup and stop it before deleting state.

Fix the cause at the appropriate spec, terminal session, runner, CLI or artifact boundary. Target selection/setup remains explicit. Framework-independent fixes include input decoding, terminal state, resize/readiness, deterministic fixture setup, path validation, export/cleanup, error reporting and recorder usability.

A finding does not authorize a speculative rewrite, new core language, paid service, game exploration or autonomous correctness inference. Larger capability gaps require a clear measured need, acceptance cases and an ADR; implement them only when necessary for the current deterministic CLI/TUI boundary. Reject hidden terminal emulation exceptions. If a requested interaction is deliberately outside scope, make the limitation clear and test safe rejection; do not promise universal compatibility.

Do not leave a critical/high Playtestr cleanup, data-loss, secret-persistence, false-pass or core-flow defect merely as backlog and continue marking projects accepted. Stop acceptance for affected paths, fix and requalify; continue independent diagnosis where possible. If an external prerequisite truly cannot be resolved, retain the precise block and complete unaffected work. Never fabricate success to reach ten.

## Safe deletion rules

Before recursive deletion resolve and inspect the absolute application directory. Require it to be a task-created descendant of the designated temporary target root, never the root itself, a pre-existing directory, workspace root, Git metadata or an unrelated resolved link/junction. Track ownership at creation; a similarly named directory is not proof. Refuse unknown/link-containing paths until checked. Verify all relevant processes/services are stopped and evidence copied/hash-checked first. If cleanup cannot be confirmed, report the retained directory and continue independent work; do not delete live state or assert removal.

On Windows use native PowerShell Remove-Item -LiteralPath with the verified full path, in one shell end to end. Do not pipe discovered paths to cmd/batch or interpolate destructive commands. Inspect deletion success and running process state. Preserve Playtestr itself and reusable source/test changes.
