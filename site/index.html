01 / THE WORKFLOW

A small test.
A repeatable interaction.

1

Start your application

Give Playtestr a command and a viewport. Your app runs in a real pseudoterminal with its normal keyboard interface.

2

Describe the interaction

Wait for visible text, send keys, and check the result. Small JSON specs keep the sequence easy to read and review.

3

Compare what users see

Assert rendered text and expected exit codes. Save a screen snapshot to catch changes in later runs.

02 / WHEN SOMETHING CHANGES

See the difference.
Keep the evidence.

A changed screen produces a text diff and a nonzero exit code. The captured screen and diff are saved beside the spec for inspection.

Try the intentional failure ↗

Runs with limits

Step deadlines, total timeouts, output limits, and process cleanup keep a hung target from holding up your test run.

Understands redraws

Assertions inspect rendered terminal text, including cursor movement, alternate screens, and viewport resizing.

Updates on purpose

Review a snapshot change before accepting it. Update a single named baseline after the test and cleanup succeed.

03 / TRY IT LOCALLY

Your first passing test.

Download the stable archive for your host, verify its adjacent SHA-256 file, extract it, and run the binary. The standalone runner does not need Go.

Playtestr runs trusted applications with your permissions. It is not a sandbox. Text snapshots exclude styles, and complex Unicode layout has known limits. Read the compatibility notes.

# after downloading the Linux amd64 files
sha256sum --check playtestr_0.1.0_linux_amd64.tar.gz.sha256
tar -xzf playtestr_0.1.0_linux_amd64.tar.gz
./playtestr_0.1.0_linux_amd64/playtestr --version
